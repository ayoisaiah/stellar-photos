Image sources worth adding

Ranked against the extension's real constraints: instant cache-first tabs, MV3 host permissions, public client code, durable reuse rights, useful attribution, and Chrome/Firefox support.

Date: 2026-08-26Topic: image-sourcesFocus: other image sources for Stellar PhotosMode: repo-grounded

Codebase Context

The existing ImageSource interface is already the right-sized seam: stable source identity, random metadata acquisition, image download, optional rotation, full download, and tracking. The ten-item Cache Storage history removes new-tab latency from most provider calls. The constraints are outside that interface: every remote origin is currently a required manifest permission; embedded API keys are public; remote URLs are strictly allowlisted; images are bounded to 20 MiB; and the attribution model cannot yet represent license name or license URL. Rich photo information is also still Unsplash-specific.

Therefore, the best additions are sources with a small, stable set of origins, explicit caching/reuse terms, strong curation, and metadata that can be preserved locally. Non-default remote sources should use optional host permissions requested when enabled.

1. Curated Art Institute “Museum mode”

Confidence 95% · Medium

Add a source restricted to public-domain Art Institute of Chicago works, with filters for image availability, usable resolution, and background-friendly aspect ratios. Use a small generated catalog or paged sampling, then request provider-recommended IIIF sizes.

Axis
Distinctive catalog
Basis
external: The official AIC API supports public-domain filtering, fixed-size IIIF image URLs, CORS, and explicit hotlinking guidance without a user API key.
Rationale
This is not “another Unsplash.” It gives Stellar Photos a recognizable cultural identity while fitting its cache and origin-validation model unusually well.
Downsides
Many works are portrait or square. Filter deliberately, preserve institution/artist/work metadata, and do not assume every API record is public domain.

2. User-owned publisher feed

Confidence 88% · Medium

Define a small declarative JSON manifest for photographers, teams, or self-hosters: stable ID, image URL, dimensions, title, creator, source URL, and license fields. The extension requests access only to the feed and image origins the user enables.

Axis
Extensibility
Basis
direct: The source-neutral asset and cache model already accepts opaque provider payloads and stable IDs; the principal missing piece is optional per-origin permission handling.
Rationale
One source unlocks S3/R2/static sites and personal curated collections without building a separate OAuth integration for every storage vendor.
Downsides
Arbitrary origins expand the security surface. Require HTTPS, explicit optional permissions, strict URL/schema validation, bounded redirects, and data-only manifests—never remote executable configuration.

3. Wikimedia Featured Pictures

Confidence 84% · High

Use only Commons Featured Pictures or Picture of the Day, not unrestricted search. Request Wikimedia-hosted thumbnails at a bounded size and persist the work page, creator, license, and license URL with every cached image.

Axis
Rights and attribution
Basis
external: Wikimedia maintains a community-curated Featured Pictures collection, while its APIs expose media and licensing metadata.
Rationale
It supplies nature, history, architecture, maps, and science at a breadth no single stock provider offers, without a secret key.
Downsides
Licenses vary, metadata may contain HTML, and media types are diverse. This needs a strict image/license allowlist, HTML sanitization, and a richer attribution model before launch.

4. Deterministic procedural art

Confidence 90% · Medium

Generate tasteful seeded gradients, geometric landscapes, or star fields locally. Treat the seed as the stable asset ID and cache the rendered result through the same history pipeline.

Axis
Offline reliability
Basis
reasoned: A local generator requires no provider permission, key, attribution, network, or policy compliance and can always produce a valid next background.
Rationale
This is the best zero-network fallback and a real differentiator. It also prevents an empty or stale experience when remote providers fail.
Downsides
It stretches the product beyond photography and quality is easy to get wrong. Position it as an explicit “Generative” source or fallback, not as a photo provider.

5. Staged open-access museum expansion

Confidence 82% · Medium

After AIC proves the product, add The Met as the second vetted museum, then extract only the shared image-delivery and attribution behavior. Consider Smithsonian or Rijksmuseum later as curated provider packs.

Axis
Permission/privacy surface
Basis
external: The Met Collection API offers no-key access to Open Access data and corresponding public-domain JPEGs. AIC already provides IIIF, demonstrating useful overlap but not identical provider semantics.
Rationale
This earns a reusable museum layer from two concrete implementations instead of guessing at a universal abstraction. Provider packs keep rights filters and origins auditable.
Downsides
Random selection may require a prebuilt index; records can lack images or suitable orientation. Do not expose arbitrary IIIF endpoints until rights and metadata behavior are understood.

6. Verified NASA-owned space imagery

Confidence 72% · Medium

Create a space source from a curated set of NASA-owned still images, using NASA's image library metadata and explicit credit. APOD may inform discovery, but third-party copyrighted entries and video must never enter the feed automatically.

Axis
Distinctive catalog
Basis
external: NASA publishes an official image library API, but its media guidance distinguishes NASA material from third-party works. APOD itself is not a blanket public-domain feed.
Rationale
Space is an unusually good thematic match for “Stellar Photos,” and a curated NASA-owned feed avoids APOD's rights ambiguity.
Downsides
Ownership and credit must be checked per asset. A conservative curated catalog is safer than random APOD dates and less operationally simple than AIC.

Rejection Summary

#IdeaReason rejected or deferred
1NASA APOD as-isRefuted: it includes video and third-party copyrighted work; API availability does not grant image reuse rights.
2PexelsRefuted: official API guidance explicitly excludes wallpaper/image-gallery products that primarily serve Pexels imagery.
3PixabayRefuted: hotlinking, caching, systematic-download, and embedded-key constraints conflict with persistent client-side history.
4FlickrRefuted for public discovery: inconsistent per-image rights, API key/commercial terms, and cache constraints add risk without strong differentiation.
5Openverse directDeferred: upstream image hosts and licenses vary, causing host-permission sprawl and unreliable runtime downloads. Better as curated ingestion or behind a controlled backend.
6Generic IIIF source nowDeferred as premature abstraction. Ship one museum, validate a second, then extract the real common seam.
7Bing Image of the Day / Google Arts scrapingRefuted: no durable supported reuse contract; brittle endpoints create legal and store-review risk.
8Google Photos / Dropbox / OneDriveDeferred: OAuth, token storage, privacy disclosures, provider verification, and cross-browser identity cost outweigh the value while local folders exist.
9Social and wallpaper feedsRefuted: moderation, NSFW exposure, provenance, and reuse rights are unacceptable defaults for a new-tab surface.
